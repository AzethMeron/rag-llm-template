# 2026-08-03 — Findings surfaced while writing the API reference (Label P)

**What was checked.** While producing the exhaustive `docs/api/` reference (every public
module/class/method/function across `ragkit`'s 9 packages and the 6 recipes, 533 items), each
writer read the real source rather than trusting a name or an existing docstring. That reading —
not a dedicated audit — surfaced a handful of real findings and some non-obvious-but-intentional
behaviors worth recording. Each is independently re-verified here against current source with
file:line, not just relayed from the writer's chat summary.

Severity here is lighter-weight than the 2026-08-02 deep audit's scale (nothing found this pass
rises to High/Critical) — just **Worth fixing** vs **Informational** (intentional, or too minor to
independently justify a change, but worth knowing).

**Resolution (2026-08-03).** After a second critical review of the five "worth fixing" items, four
were fixed (#1, #3, #4, #5) and one (#2) was re-assessed as intentional-and-left-as-is; each
finding carries its own **Status** line below. The Informational items are unchanged by design.

## Worth fixing

### 1 — `recall_at_k`/`average_precision` raise `ZeroDivisionError` on an empty `relevant` set, called directly
- **Where:** `src/ragkit/eval/retrieval.py:65` (`recall_at_k`, `len(top & relevant) / len(relevant)`) and `:94` (`average_precision`, `summed / len(relevant)`).
- **Defect:** both divide by `len(relevant)` with no guard. `recall_at_k`'s own docstring says "Undefined with no relevant ids, which the harness excludes before calling this" — true for `evaluate_retrieval` (which raises `IncompleteGroundTruthError` first), but nothing stops a caller from invoking `recall_at_k`/`average_precision` directly (they're public, exported functions) with an empty `relevant` — e.g. a recipe's own retrieval-eval loop, or a notebook. `hit_rate_at_k`, `reciprocal_rank`, and `ndcg_at_k` all handle the same input safely (return `0.0`); these two don't.
- **Failure scenario:** a caller filters queries slightly differently than `evaluate_retrieval` does and passes one with no gold ids straight to `recall_at_k` → raw `ZeroDivisionError`, not a structured, diagnostic error naming what went wrong (CLAUDE.md: "never allow failures to be silent... a bad value should be of a type that throws on any operation attempted on it" — this does throw, but with no context).
- **Suggested fix:** either guard both with the same `IncompleteGroundTruthError`-style raise the harness gives you for free today, or explicitly document (and accept) that these two are "harness-internal, always call through `evaluate_retrieval`" — right now the docstring hints at this but doesn't enforce or generalize it to `average_precision`, which has no such note at all.
- **Status (2026-08-03): FIXED.** All five metrics now raise a `ValueError` (the module's own precondition-error convention — see `evaluate_retrieval`'s `k < 1` / no-systems checks) on an empty `relevant`, via a shared `_require_relevant` guard, rather than two crashing with `ZeroDivisionError` while three returned a made-up `0.0`. Chose raise-uniformly over return-0.0 because a score for an unscorable (no-gold) query is a fabricated number, not a real one. No production path affected (`evaluate_retrieval` still excludes empty-gold queries first). Tests pin the raise for all five.

### 2 — `med_evidence/reader_eval.py`'s `main()` doesn't wrap its pipeline in the shared error handling every other recipe entry point uses
- **Where:** `recipes/med_evidence/reader_eval.py:95-119`.
- **Defect:** every recipe's `eval.py` (`legal_procurement`, `med_evidence`, `nl_to_sql`, `predictive_maintenance`, `translation`, `form_autofill`) is a pure post-hoc scoring script whose entire `build()` closure runs inside `ragkit.eval.gold.run_report`'s `try/except EvalError` (e.g. `recipes/med_evidence/eval.py:72-80`). `reader_eval.py` is architecturally different — it's a self-contained mini-pipeline (`assemble()` → `run_batch()` → `export_jsonl()` → `evaluate()`), not just a scorer — but only the gold/heldout-loading step (lines 96-97) is inside a `try/except EvalError` (lines 95-100). Lines 102-119 — `assemble()`, `run_batch()`, `export_jsonl()`, `evaluate()` — run unwrapped.
- **Failure scenario:** an unreachable model server, a bad config, or an infra failure during the actual run (`assemble()`/`run_batch()`) crashes with a raw, unstructured traceback instead of the same clean `error: ...` message + exit 1 every other recipe's entry point gives an operator.
- **Suggested fix:** wrap lines 102-118 in the same `try/except EvalError` (or a broader `except (EvalError, RagkitError)` given `assemble()`/`run_batch()` can raise other `ragkit.core.errors.RagkitError` subclasses that `run_report`'s narrower catch wouldn't handle either — worth deciding which scope is actually wanted here, since it differs from the pure-scorer recipes' need).
- **Status (2026-08-03): CONSIDERED, INTENTIONALLY NOT CHANGED.** On re-examination this is weaker than first framed. The *operator-facing* errors — a wrong `--abstracts`/`--heldout`/`--gold` path — are already caught (lines 95-100), so the "you typed the wrong path" experience is already consistent with the other recipes. The only unwrapped part is the live pipeline (`assemble`/`run_batch`), whose failures are genuine infrastructure (model server down), where a full traceback is *appropriate and informative*, and where the other recipes' `run_report` (which catches only `EvalError`) wouldn't help anyway — so "make it match the other recipes" is a false equivalence (they are pure scorers with no live dependency). Not a defect; left as-is.

### 3 — `SchemaIntrospector` can never actually see a `:memory:` store's real schema
- **Where:** `src/ragkit/store/sql/sqlite.py:115-120` (`SqliteIntrospector.__init__`/`from_config`) and `src/ragkit/store/sql/duckdb.py:104-117` (`DuckDBIntrospector.__init__`/`schema`, explicit comment at `:115`: "`:memory:` cannot open read-only; it is per-connection").
- **Defect:** a `:memory:` SQLite/DuckDB database is scoped to the single connection that created it — nothing else, including another connection opened by the *same process*, can see its tables. `SqliteIntrospector`/`DuckDBIntrospector` each open their **own** fresh connection to introspect the schema (`sqlite3.connect(self._path)` at `sqlite.py:115`-adjacent; `duckdb.connect(...)` at `duckdb.py:117`). If `self._path == ":memory:"`, that's a brand-new, empty in-memory database — never the one an `SqliteStore`/`DuckDBStore` elsewhere in the same process actually wrote to.
- **Failure scenario:** an NL→SQL recipe (or any `[introspector]` consumer) configured with `path = ":memory:"` gets an introspector that reports **zero tables**, always — not an error, just silently wrong/empty output, exactly the "silent failure" class CLAUDE.md forbids. Comments in both files show the driver authors were aware `:memory:` is per-connection (it's mentioned for the `SqlStore` side's own read-only handling) but the introspector's separate-connection consequence isn't called out or guarded anywhere.
- **Suggested fix:** either refuse `:memory:` explicitly at the introspector's construction (a clear `SchemaIntrospectorError` naming the reason, matching the pattern `SqlStoreError.schema_on_read_only()` already uses elsewhere), or document the limitation loudly in both classes' docstrings so it's at least not silent.
- **Status (2026-08-03): FIXED.** Both introspectors now refuse a `:memory:` path with a shared `SqlStoreError.memory_introspection()` (one identical message across the two drivers). Refused at `schema()` time — exactly where the 2026-08-02 missing-file guard (M15) fires — rather than at construction, so the blast radius stayed minimal (the `load_storage` wiring test that constructs but never calls `schema()` is unaffected) and the two silent-empty triggers (M15's missing file, and this `:memory:`) now fail loudly from the same place. Because `from_config`'s `path` default is `:memory:`, an `[introspector]` section with no `path` is now also refused rather than silently empty. Regression test per driver.

### 4 — `Persona`'s `from_rules`/`instructions` mutual-exclusion is enforced only by the config loader, not by the type itself
- **Where:** `src/ragkit/harness/roles.py:136-140` (`Persona.__post_init__` — validates only `kind` and `max_tokens`) vs `:282-295` (`load_panel` — validates `from_rules` requires `kind == "reviewer"`, `from_rules` and non-empty `instructions` are mutually exclusive, and at least one of the two must be set).
- **Defect:** all three invariants the class's own docstring implies (`from_rules`: "Reviewer only") are enforced only in the TOML-loading path, not in `Persona.__post_init__`. CLAUDE.md: "Preserve invariants... Invalid objects should be impossible or difficult to construct" — here they're easy to construct: `Persona(id="p", kind="producer", model="m", instructions="x", from_rules=True)` builds without error.
- **Failure scenario:** any caller that constructs a `Persona` directly rather than through `load_panel` (a test, a future programmatic API, a different config format) can silently create a producer with `from_rules=True` (documented as reviewer-only and meaningless for a producer) or a persona with both `from_rules` and real `instructions` set (one is documented to silently lose to the other downstream) — with no error at construction, only surprising behavior later.
- **Suggested fix:** move the three checks into `Persona.__post_init__` itself (moving the invariant to the type, not just one loader), and have `load_panel` rely on the dataclass raising rather than duplicating the checks — closes the gap and removes the duplication in one move.
- **Status (2026-08-03): FIXED as suggested.** The three invariants now live in `Persona.__post_init__`, so an invalid persona cannot be constructed at all; the loader's own copies are removed. `load_panel`'s pre-existing `except ValueError → ConfigError` wrapper already translates the type's `ValueError` into the same located, id-named config error, so the three loader tests were unchanged (their substrings are preserved) — this was pure duplication removal, not a message change. The `__post_init__` messages carry no `persona {id}` prefix on purpose (the wrapper adds it) to avoid a doubled prefix. Added direct-construction regression tests for each invalid state.

### 5 — `SqliteStore.__init__` opens the connection before validating a self-contradictory config, so a rejected instance leaks an open connection to GC
- **Where:** `src/ragkit/store/sql/sqlite.py:57-70`. Contrast `src/ragkit/store/sql/duckdb.py:43-51`, which validates `schema_sql and read_only` **before** opening (with an explicit comment explaining why: "so the error names the real mistake rather than a downstream open failure").
- **Defect:** `SqliteStore.__init__` opens `self._conn` (line 64-65) first, then raises `SqlStoreError.schema_on_read_only()` at line 69 if both `read_only` and `schema_sql` are set. Since `__init__` raises, the object never finishes constructing, so no caller ever gets a reference to close that connection — it's only reclaimed when Python's GC finalizes the orphaned `sqlite3.Connection`, not deterministically (CLAUDE.md: "Deterministic resource ownership... Resource leaks are unacceptable").
- **Failure scenario:** a config with `read_only = true` and a `schema_sql` both set opens (and briefly leaks) a real SQLite file handle before erroring — normally harmless (SQLite connections are cheap and GC runs eventually), but a real ordering inconsistency between the two "equivalent" `SqlStore` drivers, and the sibling `DuckDBStore` shows the fix is a small, already-proven reordering.
- **Suggested fix:** move the `schema_sql and read_only` check in `SqliteStore.__init__` above the connection-opening line, matching `DuckDBStore`'s order exactly.
- **Status (2026-08-03): FIXED as suggested.** The contradiction is now rejected before the connection is opened, matching `DuckDBStore` — so a bad config never opens (nor orphans) a file handle, and the error names the real mistake. (The original "leaks to GC" framing was slightly overstated: in CPython refcounting reclaims the orphaned connection promptly when `__init__` unwinds; the real value here is the driver-consistency and the fail-before-touching-the-database ordering.) Existing read-only+schema_sql error test still covers the raise.

## Informational (not a defect — intentional, already handled correctly, or a residual limitation with no realistic fix)

- **BM25 relevance scores differ in absolute magnitude between drivers even after the M16 unification fix.** `src/ragkit/store/lexical/bm25.py:13` (`bm25_to_relevance`) is now the single shared transform both `SqlitePairings`/`DuckDBPairings` map their engine's raw BM25 through (fixing the *original* audit finding — the two drivers used to apply genuinely different formulas). But the transform being shared doesn't make the two engines' **raw** BM25 magnitudes for the same query/corpus equal — SQLite's FTS5 `bm25()` and DuckDB's `match_bm25` are different implementations with their own internal constants, so the same monotone transform applied to two different raw inputs still yields different final numbers for the same query. This is an inherent consequence of using two different full-text-search engines, not something the M16 fix was ever positioned to close, and there's no realistic further fix short of replacing one engine's scoring internals — recorded here so nobody re-discovers it as a "regression" of the M16 fix.
- **`LanceVectorIndex.close()` is a documented no-op; `QdrantVectorIndex.close()` actually closes its client.** `src/ragkit/store/vector/lancedb.py:203-206` (comment: "LanceDB holds no long-lived handle that needs explicit release... exists for interface symmetry with the other stores") vs `src/ragkit/store/vector/qdrant.py:116-117`. Intentional and explained in-place; a caller relying on `VectorIndex.close()` for cleanup gets correct behavior from both, just via different mechanisms.
- **`DuckDBPairings.all_ids()` takes a dedicated cursor rather than the shared connection, deliberately.** `src/ragkit/store/pairings/duckdb.py:178-190` — the code comment explains this at length: DuckDB's `connection.execute()` shares one result-set per connection, so an unrelated call from another method mid-iteration would silently clobber this generator's position (verified in the comment, not hypothetical). Already correctly handled via `self._conn.cursor()`; recorded here only because it's a subtle, easy-to-regress hazard if anyone touches this method without reading the comment first.
- **`ValidatorPipeline` does not itself implement the `Validator` protocol.** `src/ragkit/harness/validators.py:132-155` — its public method is `check(...)`, not `validate(...)`, so `isinstance(pipeline, Validator)` is `False`. This is by design (`ValidatorPipeline` orchestrates a collection of real `Validator`s; it isn't one), but the name is close enough to invite a wrong assumption — worth knowing if extending this area.
- **`flags_for`'s error handling only wraps endpoint-lookup failures, not config-loading failures, into `ServeArgsError`.** `src/ragkit/llm/serveargs.py:76-82` — `load_models(config)` (line 77) runs *before* the `try`, so a malformed `models.toml` (`ConfigError`) propagates from `flags_for` as a raw `ConfigError`, not a `ServeArgsError`; only `pool.endpoint(endpoint_name)` failures (e.g. an unknown endpoint name, `ModelPoolError`) get wrapped, at line 79-81. Plausibly intentional (the config-loading error is already a clear, structured `ConfigError` on its own) rather than a bug — recorded so the asymmetry is at least documented rather than silently inconsistent.
- **Cross-recipe `Report`/scoring-base diversity is real and intentional, not an oversight.** Confirmed by reading every recipe's `eval.py`: `form_autofill`, `nl_to_sql`, and `translation` define their own bespoke `Report` (each scores something other than a single predicted label); `med_evidence` and `predictive_maintenance` subclass the shared `ragkit.eval.classify.ClassificationReport`; `legal_procurement` uses `ragkit.eval.retrieval.RetrievalScores` directly (it scores retrieval quality, not a produced label at all). Three genuinely different shapes for three genuinely different tasks — not a gap to unify.
